# /code-review xhigh — src/ (2026-11-06)

Two findings were confirmed by execution (1 and 2). The rest come from reading the code. The known stale `g_<aid>` normalizer row was excluded because CLAUDE.md already lists it.

1. **high: `src/ingestion/scheduler.py:144`.** The Whoop job reads `log.records_stored` after its session has closed, which raises DetachedInstanceError (confirmed). The except branch then deletes the Whoop token if the error text contains "401". The memory address in the error message matches about 0.2% of the time; at 48 runs a day that is roughly an 11% chance per day of a forced re-auth. Fix: capture the log fields inside the session block.
2. **high: `src/analytics/anomaly_store.py:77`.** `refresh_anomalies` recomputes over the sync window only, then deletes cached rows in that window. Incremental windows (1–3 days) can't flag anything, because `detect_anomalies` needs 7 prior values. So every sync wipes the recent anomalies (confirmed by simulation). Root cause is 6. Fix: compute over a lookback, then keep results ≥ start.
3. **high: `src/ingestion/scheduler.py:95`.** Same detached-instance bug in the Garmin job. It reads `log.status`/`records_*` after `with SessionFactory()` exits, which raises out of the job (APScheduler ERROR) and loses the status line. Tests miss it because they use a MagicMock or a detached SyncLog. Fix: capture the fields inside the session block, and add a test with a real session.
4. **high: `src/api/routes/auth.py:61`.** Open `/register` combined with `get_owner_user_id` raising on more than one user means one extra signup halts all syncing. Already a roadmap Phase 3.1 item, ruling R16.
5. **high: `config/settings.py:62`.** `JWT_SECRET` defaults to "", and python-jose signs and verifies HS256 with an empty key. Combined with `get_current_user` trusting `sub` without a DB lookup, anyone can forge an owner token. Fix: refuse to start when `JWT_SECRET` is empty. CLAUDE.md already says it "must be set even locally".
6. **medium: `src/analytics/trends.py:842` (and `:716`).** `_build_trend_from_calendar` / `get_metric_trend` fetch a 29-day lookback but run `detect_anomalies` on the window slice only, so the first 7 days of any range can never be flagged. Fix: detect on the full calendar, then keep dates ≥ start.
7. **medium: `src/ingestion/whoop_pipeline.py:218`.** The Whoop incremental window starts exactly at the previous `sync_end` with no overlap. PENDING sleep/recovery or early strain is never refreshed now that the webhook is gone (D3). Fix: add an overlap like Garmin's.
8. **medium: `src/api/routes/webhooks.py:119`.** The webhook builds `WhoopClient`/`Normalizer` without a user_id. It is unauthenticated and broken. Slated for removal (Phase 3.5).
9. **medium: `src/clients/garmin_client.py:211`.** A bearer-level rejection (double 401 / 403) raises GarminKeyError without setting `auth.last_error`, so `/api/auth/garmin/status` can keep reporting connected=true from its 10-minute cache. Fix: set `auth.last_error` there too.
10. **medium: `src/analytics/trends.py:1135` (and `:966`).** The sleep context for an anomaly looks up unified_sleep at date−1, but unified_sleep is keyed by wake date, so it reads the wrong night. Fix: use the same date.
11. **medium: `src/normalization/whoop_mapper.py:173`.** `unified_workouts.date` uses the UTC date for Whoop rows but the local date for Garmin rows, so evening sessions shift a day once matched. This is a behaviour change to the data model.
12. **medium: `src/api/routes/sync.py:168`.** Whoop syncs have no run lock (Garmin has `_RUN_LOCK`), so a manual and a scheduled Whoop sync can overlap, causing an IntegrityError and a concurrent refresh-token rotation. Related to roadmap Phase 3.6.
13. **medium: `src/ingestion/csv_import.py:300`.** `_store_json_activities` increments `stored` before `_date_from_gmt` can fail, and it assumes API shapes rather than Garmin bulk-export shapes. This is the import path for history older than 180 days. Fix: compute the date before upserting. Verifying the shapes against a real export is a decision.
14. **medium: `src/ingestion/garmin_pipeline.py:500`.** `_get_sync_window` resumes from the most recent successful log, whatever its window. A chunked historical backfill would reset the incremental start to the past. Fix: base the window on max(sync_end) across successful logs.
15. **medium: `src/api/routes/sync.py:266`.** A manual Whoop sync runs the pipeline on the event loop (blocking DB I/O), and the `create_task` result is not retained. Fix: use `asyncio.to_thread` like Garmin, and keep a strong reference to the task.

Cut for space: duplicated helpers between garmin_upload and garmin_csv (slated for removal), the unused `transform_exercise_sets` (kept on purpose, per roadmap), and a missing docstring on migration 014's `run`.
